# PB-13 handoff — ENS release publication

## Implemented locally

`integrations/ens/src/publication.ts` contains a viem ENSv2 client path:

- Candidate and approved records use distinct text keys on a configured name and resolver.
- Writes verify the selected chain and that the name currently resolves to the configured resolver. Only Ethereum mainnet and Sepolia are accepted.
- Candidate publication schema-validates the shared `ManifestSchema`, calculates the canonical keccak digest, reads the HTTPS artifact back through a caller-provided storage adapter, and rejects a mismatch before writing ENS.
- Approval reads the currently resolved candidate, checks the expected digest, verifies the artifact bytes again, rejects the same proposer wallet, and writes that exact pointer to the approved key. ENS EAC remains the actual onchain authorization boundary; PatchBond does not bypass or simulate it.
- Consumers resolve only the approved key, retrieve the bytes through an injected fetch adapter, and validate schema, release ID and digest.
- The module contains no hardcoded supplier address, resolver deployment address, ENS name, RPC URL or artifact endpoint.

## Tests and commands

`integrations/ens/test/publication.test.ts` covers canonical pointer creation, manifest-content mismatch, malformed schema/URI, independent proposer/approver addresses and supported chain IDs. `vitest.config.ts`, `tsconfig.json` and root lint scripts now include `integrations/`.

Run:

```sh
pnpm exec vitest run integrations/ens/test/publication.test.ts
pnpm exec tsc --noEmit
```

These are local behavior/type checks. They do **not** prove live ENS resolution, EAC permission setup, unauthorized-write rejection, role revocation or prize eligibility.

## Live Sepolia steps still required

1. Configure an ENSv2 Sepolia name and a resolver dedicated to this release workflow; do not use a shared resolver with unrelated names.
2. Grant the candidate engineer setter permission only for `patchbond.candidate-manifest.v1`.
3. Grant the distinct approver setter permission only for `patchbond.approved-manifest.v1`. Retain resolver root/admin control with the supplier's documented owner/multisig.
4. Using the candidate-only wallet, attempt to set the approved key and record the reverted transaction.
5. Publish a candidate with the proposer wallet; approve it with the separate approver wallet; resolve and fetch the actual manifest and verify its digest.
6. Revoke the approver's key-scoped role and demonstrate the next approved-key write reverts. Restore it only if another authorized test is needed.
7. Change the ENS approved pointer after creating a campaign and verify the campaign's already-stored policy/test-pack hashes are unchanged.

Do not broadcast role grants/revocations or publish test records until the team identifies its name, resolver, wallet roles and transaction intent. ENS publication is external chain state, not a local test fixture.

## Remaining boundary

The module is not yet called by the API, campaign-draft creation or frontend. It is an integration library and test slice. Wire it into the real campaign discovery path before submission; fetch adapters must enforce the repository's artifact-fetch restrictions (scheme/host allowlist, timeout, response-size limit, no redirects/private-network targets). Do not claim ENS as central until that end-to-end path and live permission evidence exist.
