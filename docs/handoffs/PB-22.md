# PB-22 handoff — campaign indexer and API views

**Status:** implementation is blocked on authoritative generated contract ABIs and a deployment manifest. No campaign/indexer/API code was added in this checkpoint.

## Audit findings

- The PB-22 card requires B to export the PB-15/PB-20 ABIs. This checkout has Solidity interfaces and implementations but no generated ABI artifacts or committed ABI exports.
- There is no `config/deployments/` or deployment manifest. The optional `NetworkSchema.deployments` only carries a source registry address, destination campaign address, two code hashes and two deployment transaction hashes. It has no deployment block numbers, PB-20 sender/receiver addresses, or generated contract artifact/version references.
- No live campaign deployment or campaign-specific policy/eligibility set is recorded. `docs/handoffs/PB-20.md` explicitly records no deployment, funded campaign, receipt, CCIP message, receiver transaction or destination claim state.
- The proposed financial API routes in `docs/planning/INTERFACES.md` are not implemented. The current API intentionally accepts `purpose: diagnostic` runs only and has no campaign or claim endpoints.
- PB-21 contains minimal viem read ABIs in source because a shared generated ABI export is absent. PB-22 must consume generated exports; it must not add a second manually maintained event/read ABI or accept ABI/event mappings from a browser request.

## Required inputs before implementation

1. Generated, reviewed PB-15 registry, PB-16 verifier, PB-17 campaign and PB-20 sender/receiver ABIs, with source provenance and exact contract version/hash.
2. A schema-validated deployment manifest containing chain IDs separately from CCIP selectors, each address and runtime code hash, deployment transaction and starting block, plus the selected RPC/config references. Testnet values must come from actual deployment evidence; local simulation values must be explicitly labeled.
3. Agreed chain-derived API response fields and explicit indexing provenance: chain/block/hash, finalized head, indexed-through block, lag, and rollback/reorg state. API reads may describe observed state but cannot create acceptance or payment.
4. A local integration fixture that exercises duplicate logs, checkpoint restart, removed logs/reorg, event ordering and RPC unavailability against the generated ABI.

Until those inputs exist, an indexer cannot know which events or deployment range to trust, and campaign state cannot safely be presented as live. Do not fill this gap with fixture addresses, guessed block numbers, local contract literals or seeded green states.
